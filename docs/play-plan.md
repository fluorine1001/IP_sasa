# 운이 아니라 퍼즐로: 예약의 시점과 종속성

## 0. 문제: 왜 운처럼 느껴지는가

이 게임은 완전히 결정적이다. 그런데 플레이어는 "운 좋게 됐다"고 느낀다. 원인은 무작위가 아니라 **예약의 효과가 절대 시각에 묶여 있다**는 데 있다.

- 연소를 "12.3초"에 예약하면, 그 연소가 하는 일은 12.3초에 기체가 _어디에_ 있느냐에 달려 있다.
- 그 위치는 앞의 모든 예약(발사 세기, 첫 연소)이 정한다. 앞을 조금 고치면 12.3초의 기체는 다른 곳에 있고, 뒤 연소는 전혀 다른 일을 한다.
- 즉 **한 값을 고치면 뒤의 모든 값의 의미가 바뀐다**(숨은 종속성). 그리고 같은 0.1초가 근점 근처에서는 큰 차이, 원점 근처에서는 작은 차이를 만든다(**변화 폭이 시각마다 다름**).
- 플레이어는 "내가 바꾼 것"과 "바뀐 결과"를 연결할 수 없다. 데이터를 쌓아도 앞이 바뀌면 뒤 데이터가 무효가 되므로, 데이터를 논리적으로 쓸 수 없다.

## 1. 해결의 축: 예약을 사건에 묶는다

예약이 "몇 초"가 아니라 **"무슨 일이 일어날 때"** 실행되게 한다. 그러면 앞 예약을 고쳐도 뒤 예약이 하는 일(어느 자리에서 어느 방향으로 얼마나)은 그대로다.

| 실행 시점      | 뜻                              | 앞을 고쳐도 유지되는 것       |
| -------------- | ------------------------------- | ----------------------------- |
| 시각           | 정한 초에                       | (없음: 위치가 앞에 달려 있음) |
| 앞 예약 뒤 N초 | 앞 예약이 _끝난_ 뒤 N초         | 앞 예약과의 간격              |
| 근점 / 원점    | 다음 가장 낮은/높은 점          | 궤도 위의 자리                |
| 위치각         | 천체 둘레의 정한 각도를 지날 때 | 지도 위의 자리                |
| 목표 각도      | 목표가 정한 각도만큼 앞설 때    | 목표와의 위상                 |
| 목표 접근      | 목표에서 정한 거리 안에 들 때   | 목표와의 거리                 |
| 높이           | 내려오며 정한 높이를 지날 때    | 표면 위 높이                  |

근점·원점·각도·접근 예약도 "앞 예약 끝난 뒤부터 기다리기"를 고를 수 있다("연소 1 → 다음 원점"). 시계와 무관한 사슬이 된다. 발사는 엔진이 처음 꺼질 때(Δv 도달, 연료 소진, 끄기) 끝난 것으로 본다.

### 종속성은 보이게

- 예약 창 맨 위에 "〈앞 예약〉 → 이 예약"이 그림으로 나온다.
- 시간선에서 이어진 예약은 분홍 괄호로 묶인다.
- 앞 예약을 옮기면 뒤 예약도 함께 옮겨진다("이 예약을 따르는 예약 N개 · 함께 움직임").
- 앞 예약을 지우면 뒤 예약은 그 앞의 예약에 다시 이어지고(간격 합산), 없으면 그 시각으로 고정된다.
- 두 번째 이후 속력 변화는 기본으로 앞 예약에 이어진다.
- 위치각·목표 각도는 작은 그림(천체, 궤도, 기체 자리, 목표 자리)으로 보여 준다.

### 크기를 추측하지 않아도 되는 예약

- **상대속도 맞추기**(목표 대비 반대 방향)는 그 방향의 상대 운동이 사라지면 스스로 멈춘다. 접근 속도를 몰라도 되고, 앞을 고쳐도 이 예약은 다시 맞출 필요가 없다.

## 2. 변화 폭을 사람 손에 맞춘다

- 냉가스 발사 세기는 0.1% 단위로 입력한다(계산기가 발사 직후 궤도를 정확히 보여 주므로 겨냥할 수 있다).
- 위치각은 1° 단위, 간격은 0.01초 단위. 같은 1°는 궤도 어디서나 비슷한 효과를 낸다(시각과 달리).

## 3. 공정성 검사: "앞은 대충, 뒤는 겨냥"

`npm run audit:margins`는 각 임무의 기준 계획에서 값 하나를 여유만큼 바꿔 본다.

- 그대로 이기면 통과.
- 지면, 플레이어가 하는 대로 **마지막 수정(필요하면 그 앞의 것까지)만 다시 겨냥**해 이길 수 있는지 본다. 마지막 수정은 기록에서 상태를 읽는 계산기로 겨냥하는 값이기 때문이다.
- 이것도 안 되면 그 임무는 "운"이다. 설계를 고친다.
- 슬라이더 끝(최대 출력)과 기본값(맞추기 기울기 0°)은 추론이 아니라 그대로 두는 값이므로 흔들지 않는다.

기준 계획은 모두 사건 예약으로 다시 썼다(`scripts/solve-mission.mjs`):

| 임무        | 사슬                                                       |
| ----------- | ---------------------------------------------------------- |
| 3 달 착륙   | 발사 → 분리 → 다음 원점에서 전이 → 30초 뒤 수정            |
| 4 화성 위성 | 발사(Δv) → 분리 → 수정 → 화성 근점에서 감속                |
| 5 우편 위성 | 발사(Δv) → 분리 → 원점 전이 → 수정 → 목표 접근 시 맞추기   |
| 9 착륙      | 높이에서 감속                                              |
| 10 동행     | 발사(Δv) → 목표 접근 시 맞추기                             |
| 12 부스터   | 발사(Δv) → 분리 → 원점에서 원궤도 / 부스터는 높이에서 감속 |
| 14 두 궤도  | 위치각에서 전이 → 다음 원점에서 원궤도                     |
| 7, 8        | 발사 → 2초 뒤 작은 수정                                    |

| 6 달의 도움 | 발사 창(달이 −165° 앞설 때 발사) → 1초 뒤 작은 수정 |

### 발사 창: 발사 자체도 사건에 묶는다

패드 발사(냉가스와 로켓 모두)는 "바로" 또는 "목표 각도"에서 떠날 수 있다(`RoutePlan.launchHold`). 기체는 패드에서 기다리고, 목표가 패드보다 설정한 각도만큼 앞서는 순간 발사된다. 기다림은 임무 시간을 쓰고 수정 추진 한도는 쓰지 않는다. 천체는 정해진 궤도를 돌므로 발사 시각은 미리 계산해 팝오버 머리와 시간표 칩에 보인다(기체 경로 예측이 아니다).

이것이 6의 바늘 문제를 풀었다. 이전에는 달과의 만남 시각이 발사 세기에 묶여 있어 세기 0.5% 오차가 플라이바이 전체를 무너뜨렸다. 이제 "언제 만나는가"는 발사 창 각도가, "얼마나 높이 가는가"는 발사 세기와 직후 수정이 맡는다. 두 손잡이가 서로 다른 것을 바꾸므로 플레이어는 하나씩 겨냥할 수 있다. 공정성 검사도 같은 순서로 다시 겨냥한다(직후 수정 크기, 필요하면 창 각도까지). 패드에 수평이거나 수직인 발사 방향은 정확히 입력하는 값이라 흔들지 않는다.

남은 과제: 5는 발사 Δv +2%에서 한 곳이 남는다.

## 3a. 근거: 사람이 실제로 겪는 문제 → 원칙 → 바꾼 것

| 사람의 문제                             | 원칙 (출처)                                                                               | 바꾼 것                                                                 |
| --------------------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 실패가 내 탓인지 운인지 모른다          | 공정한 실패는 내부·구체적 원인으로 읽힌다 (Juul, _The Art of Failure_)                    | 사건 예약, 다시 겨냥 공정성 검사, 발사 창                               |
| 한 번 고치면 앞서 맞춘 것이 다 깨진다   | 조작 사이의 결합을 줄여 하나씩 배울 수 있게 (KSP 기동 노드: 기동은 궤도 위 사건에 붙는다) | 앞 예약 뒤·근점·원점·각도·접근 트리거, 사슬 표시                        |
| 시도 비용이 비싸 실험을 꺼린다          | 실패가 싸야 호기심이 이긴다 (Outer Wilds: 짧은 고리, 지식만 남는다)                       | E로 끝까지 비행, Ctrl+Z 되돌리기, 기록 누적                             |
| 화면이 정보로 가득해 무엇을 볼지 모른다 | 그림이 먼저, 글은 최소 (ONI의 손그림 오브젝트와 큰 아이콘)                                | 역할 기반 디자인 시스템(`docs/design-system.md`), 손그림 천체·기체·장치 |

결론이나 "무엇이 쌓이고 있다"는 해석은 여전히 보여 주지 않는다. 지표와 기록은 사실만 보이고, 무엇을 개선할지는 플레이어가 정한다.

## 3b. 불확실성: 없애는 것이 아니라 종류를 고른다

운처럼 느껴지던 원인은 주사위가 아니었다. 물리는 처음부터 결정론적이었고, 문제는 민감도였다. 결과를 재현할 수 없거나, 무엇이 결과를 바꿨는지 알 수 없는 것이 나쁘다. 불확실성 자체는 재미의 원천이므로 남긴다 (Costikyan, _Uncertainty in Games_; Poly Bridge는 결정론적이지만 결과를 다 예측할 수 없어 시험이 즐겁다).

- **남긴다 · 해결자의 불확실성**: 답을 아직 모른다는 것. 퍼즐의 본체다.
- **남긴다 · 창발적 불확실성**: 계산기는 한 천체 궤도만 보여 주고, 실제 비행은 여러 천체를 함께 받는다. 그 차이는 비행해 봐야 드러나지만, 같은 계획은 언제나 같은 결과를 낸다. 놀람은 있되 재현되고 원인을 추적할 수 있다.
- **줄인다 · 결과 민감도**: 앞 예약을 조금 바꾸면 뒤가 모두 무너지는 구조. 사건 예약, 발사 창, 궤도 기준 크기로 다룬다.
- **넣지 않는다 · 다시 깨기 위한 장치**: 한 임무는 한 번 깨면 된다(Poly Bridge처럼). 클리어 뒤 변주와 해법 기록은 만들었다가 뺐다. 임무 안의 시도 기록과 다시보기는 퍼즐을 푸는 도구라 그대로 둔다.
- **넣지 않는다 · 크기를 알아서 정해 주는 예약**: "원점 높이가 될 때까지" 같은 자동 크기는 만들었다가 뺐다. 오차를 흡수해 주는 만큼, 얼마나 밀지 추론하는 일(퍼즐의 본체)을 게임이 대신한다. 시점은 사건에 묶되, 크기는 플레이어가 정한다.

## 4. 하지 않는 것

- 게임이 "무엇이 쌓이고 있다"거나 "이렇게 고치라"고 결론을 제시하지 않는다. 데이터를 어떻게 쓸지는 플레이어 몫이다. 게임은 그 데이터가 **논리적으로 쓰일 수 있는 구조**(앞을 고쳐도 뒤가 무효가 되지 않는 구조)만 보장한다.
